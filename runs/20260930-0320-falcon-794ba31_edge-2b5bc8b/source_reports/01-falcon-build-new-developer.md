## Executive summary

Falcon-build is the implementation artifact of a single-host network-monitoring lab (Docker
Compose central + probe stacks, Suricata/Vector/OpenSearch/Prometheus/Grafana/ntfy, plus a
WireGuard VPN and a recent MCT security-stack consolidation). It is unusually rigorous: every
claim has raw evidence with hashes, gate ledgers are append-only, a review package is
cryptographically manifested, and the publication chain verifies. The core static checks are
green **today**: `ci/validate.sh` → 0 failures; `verify_publication_chain.sh` → 0 failures;
`evidence/MANIFEST.sha256` (930 entries) and `review-package/MANIFEST.sha256` (2,043 entries)
verify completely; secret scan of the review package → `NO_FINDINGS`.

The central problem for a new developer is **current-state drift after the Phase 9 production
closure (2026-09-29) and the review-fix rounds of 2026-09-29/30**. The artifacts that a newcomer
would naturally trust first — `PACKAGE_DIGEST.txt`, `AGENTS.md`, `README.md`,
`closeout/FINAL_RESPONSE.json`, the contradiction ledger, several runbooks, and the architecture
port matrix — were not updated (and in two cases are *generated by scripts that hardcode the old
state*, so re-running them will not fix it). A new developer reading `PACKAGE_DIGEST.txt` and
`AGENTS.md` today would conclude P8-G10 and most Phase 9 gates are still open and production is
**NOT_SUPPORTED**, while the ledgers and the published `PRODUCTION_VERDICT.md` say the opposite
(**APPROVED**, all 13 applicable Phase 9 gates PASS, P8-G10 reconciled). Conversely, the
delivered repomix pack is stale, so the "packed-only reviewer" verification path claimed in the
gate ledger **fails** (23 mismatched / 933 missing files) if a newcomer follows it.

Spot-checking live state (read-only) shows the stack really is running: falcon systemd timers are
active, Traefik answers on 443 (200 for Grafana, 302 for IRIS/SOC), OpenSearch answers 401
without credentials, enrollment `/health` returns 200, and the textfile metrics are fresh.
The repo is coherent where it counts mechanically, but **onboarding relies on tribal knowledge**
(which document is current, what actually runs where, which scripts are dangerous) that is not
written down anywhere reliably.

## 1. System reconstruction (what this is, how it works, how it is operated)

### 1.1 Purpose and doctrine

`falcon-build` is the repository behind the "Falcon" modular network-monitoring lab. Its doctrine
(prompt-pack): **evidence-first, least privilege, reproducible builds, append-only closeout, no
fabricated execution**. Everything done on the host is supposed to have:

1. a **gate** (§1.5) that the work serves,
2. a raw **evidence capture** produced by `automation/evidence/capture.sh` (UTC timestamps, actor,
   command, exit code, SHA-256, redaction statement, interpretation),
3. a **ledger** entry (gate / test / risk / exception / contradiction / decision),
4. a phase **closeout**, and
5. a **delivery** (review package + digest + archive) whose integrity chain can be re-verified.

## 2. Onboarding experience assessment

### 2.1 What is clear

- The **doctrine** is stated up front and is consistent across AGENTS/REPOSITORY/README.
- The **evidence format** is excellent: every capture has a `.meta.json` with command, exit code,
  hash, actor and interpretation; the manifest verifies byte-for-byte.
- **Runbooks are genuinely detailed** and largely executable (SENSOR_SILENCE, DISK_PRESSURE,
  RESTORE, UPGRADE_ROLLBACK, CERTIFICATE_AND_SECRET_ROTATION, INCIDENT_RESPONSE,
  CAPACITY_AND_TELEMETRY, VPN, WAZUH_INTEGRATION, SITE_HOST_ONBOARDING).
- **Dashboards-as-code** and **alert catalogue as code** exist; the alert catalogue carries the
  PromQL expression, runbook mapping and test evidence per alert.
- The **publication chain checker** is a real, working mechanism: it caught nothing today because
  it is green — and I reproduced it green (0 failures).
- `docs/phase9/review/` is a clean example of reviewer/owner separation and digest binding.

### 2.2 What is confusing / implicit knowledge required

1. **Which document is "current"?** The repo has at least six layers that describe state
   (README, AGENTS, PACKAGE_DIGEST, gate ledgers, decision log, FINAL_RESPONSE, phase9 review).
   They disagree today, and no single generated "current state" page exists.
2. **Append-only vs update**: a developer must learn that records are never edited, so the
   *newest* row wins (e.g. exception EX-19 has an OPEN row and a CLOSED row; EX-01 has
   PENDING_ACCEPTANCE and ACCEPTED rows; the contradiction ledger still shows C-04/05/06/08 OPEN
   though Phase 9 resolved them). Nothing states "search for the latest row" or links old rows
   to their successors.
3. **Root + secrets**: essentially every meaningful command needs root, the docker socket, or
   `/srv/falcon/secrets/*`. Without the owner's sudo password a newcomer cannot run
   `docker ps`, `docker compose config`, any health checker, or the publication tooling
   (`build_review_package.sh` is `sudo`-run in AGENTS yet writes a user-owned package).
4. **What actually runs where**: Wazuh and IRIS live in `/opt` (outside the repo), the IRIS
   compose file in the repo is a sanitized copy, OpenCanary reads `/opt/mct-security-stack/...`,
   and the edge control plane belongs to a **different repository** (`falcon-edge-build`) that
   is not named in the root README/AGENTS/REPOSITORY at all. The review package cannot carry
   those `/opt` states, so "reproduce the stack" and "what is running" diverge.
5. **Two projects in one tree**: `mct/` is an imported MSSP project with its own README,
   ARCHITECTURE, REPO-MAP, badges pointing at `github.com/MaineCyberTech/soc` and paths rooted
   at `/opt/mct-security-stack`. Nothing at the root tells a newcomer whether `mct/` is an
   archive, a vendored doc set, or live code. (It is a mix: IRIS/OpenCanary are live from it.)
6. **Dangerous tools are not flagged as dangerous** (see F-03): `test_closed_mode.sh` restores
   the *open* inbound firewall in its EXIT trap; `probe_pipeline_test.sh` stops the central
   aggregator. Both are linked from docs meant to be followed literally.
7. **Gate vocabulary**: "gate", "REVIEW-FIX", "publication", "review-package", "closeout",
   "delivery" each mean something specific; AGENTS explains the flow but not how to find the
   right gate for a change (e.g. which gate a Vector config change serves).
8. **Historical vs live names**: `mon` (old host name) appears throughout evidence, the evidence
   index, the port matrix, architecture docs and closeouts. Historical names in *evidence* are
   doctrine, but current docs still use them.
9. **Tests were built for the pre-2026-09-24 topology**: the synthetic `veth-span-b` test path
   still exists in `bootstrap/70` and `probe_traffic.sh`, while the running Suricata captures
   `ens19` only; `probe_pipeline_test.sh` now passes on ambient real-feed traffic rather than
   proving the synthetic path it describes.

### 2.3 Missing or wrong steps/examples

- README "Quick start" (`sudo bootstrap/run-all.sh` then `docker compose up`) **cannot work on a
  clean host**: `run-all.sh` never runs `50-secrets.sh`, so `/srv/falcon/secrets/central.env`
  does not exist and both compose renders/ups fail. Only `RESTORE.md` notes the 10-40 limitation.
- No "new machine" bootstrap for the *review tooling* itself (Python 3 + PyYAML; `jq`; docker
  CLI). `ci/validate.py` needs PyYAML; nothing documents that.
- No example of a **complete normal change** (e.g. adding one alert) end-to-end; AGENTS gives the
  command list but not the gate choices, evidence naming, or the commit split.
- The standard change flow in AGENTS starts at "capture evidence", but `capture.sh --sudo`
  reads the sudo password from `/home/user/.env` key `sudo`, which only the owner has.
- No local development path (everything is host-coupled). There is no CI workflow in
  `.github/` and no git hook, so the "`ci/validate.sh` must pass before committing" rule is
  pure discipline. (Hooks directory contains no active hooks.)

### 2.4 Naming/structure/discoverability

- Naming chain is confusing: project = *Falcon*; repo = `falcon-build`; sibling repo =
  `falcon-edge-build` (edge); old host = `mon`; containers `falcon-central-*` /
  `falcon-probe-*`; the edge program calls the lab its "control plane".
- `docs/architecture/` looks current but contains Phase 0 drafts: it claims a synthetic capture
  interface, no VPN, no ntopng deployment, and a `cadvisor` exporter that does not exist in
  compose/prometheus config. It is still the first thing linked under "Architecture".
- `docs/phase9/` mixes a frozen charter ("verdict remains withheld") with the final verdict.
- `evidence/phase0/` exists as a directory, so docs referencing `evidence/phase9/...` look
  plausible but are wrong (the files are under `evidence/raw/P9-*`).
- The root README points at `/home/user/falcon-full-review-2026-09-23.md` and
  `/home/user/falcon-audit-2026-09-24.md` — host files, not in the repository, so a cloned tree
  cannot follow them.

## 4. Findings

Severity: **High** = would cause a newcomer to do the wrong thing or publish a false statement;
**Medium** = significant confusion/effort or an inaccurate operational instruction; **Low** =
cosmetic/consistency; **Info** = context.

### F-01 (High) — The "authoritative" digest contradicts the ledgers and the production verdict

- **Evidence:** `PACKAGE_DIGEST.txt` says `program_verdict=INSUFFICIENT_EVIDENCE`,
  `production_readiness=NOT_SUPPORTED`, `open_gates=P5-G02 … P8-G10 …`, and
  `phase9_charter=… production gates BLOCKED on owner inputs` (lines 10-15). The ledgers show
  P5-G02 PASS since 2026-09-24 and P8-G10 PASS since 2026-09-29; the phase 9 ledger shows 13
  PASS (P9-G02/G10/G11/G12/G14 all PASS) and `PRODUCTION_VERDICT.md` says **APPROVED**
  (2026-09-29). The values are **hardcoded** in `automation/validation/publish_digests.sh`
  (lines 30-35), so the digest can never self-correct, and
  `verify_publication_chain.sh` does not check them.
- **Impact:** a newcomer, reviewer or auditor reading the published digest (the artifact the
  project itself calls authoritative) gets the opposite of the recorded gate state.
- **Recommendation:** generate `program_verdict`, `production_readiness`, `open_gates` and the
  phase-9 line from the two ledgers + a `docs/phase9/review/PRODUCTION_VERDICT.md` pointer;
  extend `verify_publication_chain.sh` with a cross-check (e.g. no INSUFFICIENT_EVIDENCE gate
  may appear as an "open gate"; phase9 PASS count must include the N/A count).

### F-02 (High) — Agent onboarding doc (`AGENTS.md`) directs work at already-closed gates

- **Evidence:** `AGENTS.md` lines 71-74: "Open program gates: P8-G10 (production verdict);
  phase 9: P9-G02/P9-G10 (IE), P9-G11/P9-G12/P9-G14 (BLOCKED, owner/reviewer)". All are PASS
  in the ledgers. (Same problem in `README.md` lines 8-13, which still describes the
  2026-09-24 state, and in `REPOSITORY.md`.)
- **Impact:** an AI agent or new engineer following the instructions will try to "close" gates
  that are done, miss the actual open work, and may re-generate stale artifacts.
- **Recommendation:** replace the static lists with a generated "current state" block (or point
  to `ledgers/*.csv` and a new `docs/CURRENT_STATE.md`), and make updating it part of the
  publication flow.

### F-03 (High) — Operationally dangerous scripts are linked without warnings

- **Evidence:**
  - `automation/vpn/test_closed_mode.sh` traps EXIT with
    `restore() { bootstrap/32-inbound-mode.sh open; }` (line 9) — running it leaves the host in
    the temporary **open inbound** mode. The Phase 9 ledger explicitly records that it "must NOT
    be run as-is" (P9-G03 note), yet `docs/phase9/VPN_ONBOARDING_CHECKLIST.md` step 5 instructs
    operators to run it, with no warning.
  - `automation/validation/probe_pipeline_test.sh` stops the central aggregator
    (`DC stop vector-aggregator`, line 57), but `docs/runbooks/OPERATOR_START_HERE.md` lists it
    under "Quick health checks" without a mutation warning (the reviewer checklist elsewhere
    says these mutate by design).
- **Impact:** a first-week operator following runbooks can open the firewall or take ingestion
  down thinking they are "checking health".
- **Recommendation:** add a `WARNING`/`DO NOT RUN without …` block at the top of both scripts,
  fix the checklist to reference the safe DO-specific battery
  (`automation/validation/phase9_vpn_do_tests.sh`), and move `probe_pipeline_test.sh` out of
  "quick health checks" into a "mutating tests" section.

### F-04 (High) — README quick start cannot deploy the stack

- **Evidence:** `README.md` line 37 says `sudo bootstrap/run-all.sh` is the deploy; `run-all.sh`
  contains only stages 10, 20, 30, 40. Secrets (`50-secrets.sh`), central (`60`), probe (`70`),
  alerting (`90`), dashboards (`91`) are never run. The compose files require
  `/srv/falcon/secrets/central.env`; `docker compose -f compose/central/... config` fails
  without it (confirmed as user: permission denied; on a fresh host it would not exist).
  `docs/phase7/runbooks/RESTORE.md` line 87 states the limitation correctly — the README does not.
- **Impact:** a new developer following the README on a clean host concludes the repo is broken.
- **Recommendation:** either make `run-all.sh` run all stages with an explicit `--full` flag, or

## 5. Onboarding friction (first week)

Ordered roughly as a newcomer would hit them:

1. **Day 0, no root:** `docker ps`, compose validation, health scripts, and `ci/validate.sh`'s
   secret-scan are the only things available; everything else needs the owner's sudo key.
2. **Which document is current?** Six competing sources; README/AGENTS/PACKAGE_DIGEST all stale
   in the same direction (pre-Phase-9), while the truth lives in `ledgers/` + `docs/phase9/review`.
   No generated index of "latest decision per topic".
3. **Append-only decoding:** duplicate rows, "(updated)" rows, superseding closeouts — a reader
   must reconstruct history manually to answer "what is true now".
4. **Deploying/verifying a change:** the AGENTS flow assumes experience (which gate? which
   evidence name? when to rebuild the package vs just the digest?). One wrong ordering step
   silently produces stale artifacts (exactly what F-05/F-06 show).
5. **Dangerous tooling:** no warning banners; two documented commands can open the firewall or
   stop ingestion.
6. **Broken helper scripts:** `test_tunnel.sh` (wrong port), `probe_pipeline_test.sh` (tests a
   retired path), `bootstrap/70` (re-introduces the retired veth), `preflight.sh` (fails on a
   deployed host).
7. **Environment split:** services in `/opt`, a sibling repo (`falcon-edge-build`), and an
   imported second project (`mct/`) make "the system" bigger than the repo map suggests.
8. **Naming:** mon/falcon, falcon/falcon-build/falcon-edge-build, gates vs phases vs WS vs N/U
   review IDs.
9. **Cross-referencing:** docs reference evidence by capture name rather than path; finding the
   raw artifact means grepping `ledgers/evidence_index.csv` (whose paths are partly
   host-relative, F-15).
10. **No sandbox:** there is no way to exercise the pipeline locally; learning by running things
    means touching the live production-target host.
